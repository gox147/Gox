# Gox 性能基准与 GC 毛刺判定（M9）

本文是 **M9「并发与性能」的可复现基准设施**的说明与数据存档。它只回答两件事、
并且**只用数字说话**：

1. **解释器算力**：gox 相对 goja（同类纯解释器）与 node/V8（JIT）到底差多少？
   → 见 [§2](#2-解释器算力基线) / [§3](#3-算力真相扣掉启动开销后)。
2. **UI 有没有 GC 毛刺**：持续高频更新下帧间隔尾部与 GC 停顿有多大？
   → 见 [§5](#5-ui-帧率--gc-毛刺基准)。

> 本轮**只做基准设施与数据**，不改 `vm/` 与 `gfx/` 的内核。内核优化（inline
> cache、降分配等）由下一轮做；本文给出的差距数字就是下一轮的验收靶子。
>
> **真机**侧指标（屏幕密度、触控与多指手势、帧率、内存 PSS、冷启动）不在本文

## 2. 解释器算力基线

**命令**（详见 [§9](#9-复现命令)）：

```bash
export PATH="/Users/apple/.workbuddy/binaries/go/bin:$PATH"
export GOPROXY=https://goproxy.cn,direct
./scripts/bench-all.sh --runs 5
```

三个脚本见 `scripts/bench/`：`startup_idle.js`（引擎启动 + 最小求值）、
`fib28.js`（`fib(28)` 递归 + 10 万次函数调用）、`timers_10k.js`（1 万次
`setTimeout(…,0)` 全部触发）。**每项外部 wall time 跑 5 次取中位数**，
RSS 取进程常驻峰值（GNU `time -v` 或 BSD `time -l`）。

| 栈 | 启动 (ms) | fib28+10万次调用 (ms) | 1万次定时器 (ms) | 空载 RSS (KB) |
|----|-----------|----------------------|------------------|---------------|
| **gox** | 11 | **322** | 124 | 22592 |
| **node (V8)** | 55 | 45 | 152 | 48432 |
| **goja** | 7 | **137** | 121 | 7792 |

口径诚实性：

- `fib28_ms` 是**整脚本 wall time**，含引擎启动 + 解析 + 求值。
- `timers10k_ms` 对外部计时；gox/node 用各自真实定时器子系统，**goja 用一个
  最小事件循环补齐**（goja 内核不提供宿主定时器，见 [§8](#8-goja-对照的口径与局限)），
  因此 goja 的定时器列**不能**当作"goja 运行时调度器性能"，只作参考。
- RSS 是**空载启动后常驻峰值**，不同后端的基线差异大（node/V8 自带一个大堆），
  它衡量的是"空壳内存"，不是算力。

## 3. 算力真相：扣掉启动开销后

`fib28` 的 wall time 里混着启动，直接拿原始值比会失真——尤其 node 的启动
（55ms）比它的 `fib28` 总耗时（45ms）还大，说明这一列几乎全是启动噪声。

用 `startup_idle` 的中位数做启动基线相减，再用 node 的 `process.hrtime.bigint()`
量**纯计算段**（`node -e` 内联同一段 fib/loop，排掉进程与文件加载）：

| 栈 | fib28 纯计算估算 | 相对 gox |
|----|------------------|----------|
| gox | 322 − 11 ≈ **311 ms** | 1.00× |
| goja | 137 − 7 ≈ **130 ms** | **0.42×**（goja 比 gox 快 2.4 倍） |
| node/V8 | ≈ **5 ms**（hrtime 内联口径） | **0.016×**（V8 比 gox 快约 62 倍） |

**诚实陈述**：

- gox 是**纯解释器**（零 cgo、直接遍历字节码）。它与 V8 的差距里，绝大部分是
  **"解释器 vs JIT"的固有差距**，不能都算成 gox 的实现缺陷。
- 真正该对标、也真正暴露实现差距的是 **goja（同样纯解释器）**：gox 的 fib28
  比 goja **慢约 2.4 倍**。这是 M9 下一轮 inline cache / 快速路径优化的直接靶子。
- 换个角度：仓库旧数据里的"落后 V8 ~15 倍"是**原始 wall 比值**（332/19）；按
  **纯计算**口径，gox 与 V8 的差距是 **~60 倍**量级。两个数都对，但口径不同，
  引用时必须说清用的是哪个（本文以纯计算口径为准）。
- gox 的**定时器吞吐已与 goja 同级**（124ms vs 121ms，差 2%），甚至快于本机
  node 的 152ms；**启动开销也小**（11ms vs goja 7ms、node 55ms），空载 RSS
  7.8MB（goja）/22.6MB（gox）/48.4MB（node）。**短板集中在纯计算热循环**。

### 3.1 "同级"的量化定义（本文采用）

`fib28` 纯计算满足下式即视为"与 goja 同级"：

```
gox_fib28_compute ≤ goja_fib28_compute × 1.25     // ±25% 容差
```

- 达标：≤ ×1.25；优良：≤ ×1.10；未达标：> ×1.25。
- 用纯计算而非原始 wall，是因为两者启动都在 10ms 量级、对 ~300ms 的测量影响 <4%，
  而原始值在 node 那一列会被启动噪声主导。
- 首测（2026-10-28）：`311 / 130 ≈ 2.39× > 1.25` → 未达标。
- **最新（2026-11-17 定稿批，§3.3）**：`263 / 256 ≈ 1.03×` → **达标**（落到 ×1.10
  的"优良"档）。口径提醒：这台机器上 goja 自身偏慢（256ms vs EPYC 上 185ms），
  **比值可信、绝对值不可跨机比**。
- 对 node 的 3 倍红线为什么不成立，见 §3.4（用"每指令成本"把这件事算成算术）。

### 3.4 对 node 3× 红线的可达性评估（2026-11-19 夜批，实测口径）

背景：2026-11-04 拍板"四条线排序：冷启动 > 引擎热点 > 多屏渲染 > 内存"，其中
"对 node 设红线 —— fib28 差距收敛到 3 倍以内"。§3.3 如实记录了 5.72× 未达标并
建议改口径，但**未拍板前照旧如实报未达标**。本节把"到底能不能做到"从判断变成
可复核的算术，供拍板用。

#### 3.4.1 每指令成本：12.9ns

一次性插桩（在 `runFrom` 的分派点累加，测完即撤，未入库）拿到 fib28 脚本的
字节码条数，再用同一脚本的 wall time 除：

| 项 | 值 |
|---|---|
| 执行的字节码条数 | **15,355,729** |
| wall（含解析 + 编译 + 启动） | 198 ms |
| **每指令成本** | **12.9 ns** |
| 分配 | 403,581 次 / 9.25 MB（平均每 38 条指令一次） |

同机 `node`（V8/JIT）的 fib28 纯计算 ≈ 5 ms（§3 的 hrtime 内联口径），
等价每指令 **0.33 ns**。也就是说：**每条指令差 ~39 倍**。

#### 3.4.2 红线换算成每指令成本

3× 红线（原始 wall 口径，与 §3.3 的 5.72× 同口径）要求 gox 的 fib28 wall
≈ node×3。本机 node 30ms → 目标 **90ms** → **5.9 ns/条**。

即需要在**当前 12.9ns 的基础上快 2.2 倍**。而 goja（同为纯解释器）也在 12ns
量级 —— §3.3 的 1.03× 正是这个意思。所以红线的实际含义是：

> gox 要比**同类解释器快 2.2 倍**，同时与 **JIT 的差距不超过 3 倍**。

#### 3.4.3 为什么这条在现架构下做不到

`pprof`（fib28，`-benchtime 10x`，Total samples 2.19s）的成本结构：

| 项 | flat | 说明 |
|---|---|---|
| `runFrom` 本体 | **34.7%** | switch 分派 + 栈操作 + 被内联的简单 case |
| `Stack.Push` / `Pop` | 12.3% | interface 槽的写屏障 + 长度维护 |
| 取指（`ReadOperand` 及内联副本） | 7.8% | 两条 3 字节指令的边界检查 |
| `callClosure` | 5.5%（cum 14.2%） | 每次调用一次帧装配 + 参数绑定 |
| `acquireFrame` / `popFrame` | 8.2% | 帧池已存在，剩下的是字段装配与 `clear(Locals)` |
| `NewNumber` 装箱 | 4.1% | 40 万次堆分配，全在数字结果上 |

要压到 5.9ns/条，必须同时动三件事，且三件都是**重写执行核心**级别：

1. **值表示换成 tagged union / NaN boxing**：`object.Value` 是 interface，
   每次数字结果装箱一次堆分配（`NewNumber` 的 `&Number{...}` 逃逸）。这是
   `object` 全包的签名变更，波及 stdlib / gfx / vm 几乎所有调用点。
2. **寄存器式字节码**：现在是栈式（Push/Pop 12%），寄存器式能把这 12% 折掉
   大半，但要重写 `compiler` 与全部 200 多条 opcode 的语义。
3. **直接线程化分派**：Go 没有 computed goto；用 handler 表 + 尾调用在本仓实测
   反而更慢（无法内联，且 `for { switch }` 已被编译器优化成跳转表）。

工作量估算：1 + 2 是 2~3 周的重写，且 test262 五万条用例要全量回归；3 在 Go 上
收益为负或接近零。

**结论：3× 在"纯解释器 + 栈式字节码 + interface 值表示"这套架构下结构性不可达。**
这不是实现缺陷 —— gox 对 goja 已经 1.03×，说明解释器本身的实现没有明显短板；
差的 39 倍里绝大部分是**解释器 vs JIT** 的固有差距（§3 的免责说明说的就是这件事）。

建议（**待 owner 拍板**，未拍板前继续如实报 5.7×/6.7× 未达标）：把红线改成
"对 goja ≤ ×1.25（已达成）+ 对 node 的倍数如实并列 + 纯解释器 vs JIT 免责说明"，
与对外口径的写法保持一致（§3.3 的定稿批就是这么写的）。

#### 3.4.4 本轮试过并撤回的（留痕，避免下一批重做）

| 尝试 | 实测 | 处置 |
|---|---|---|
| 取指合并：`ReadOpcode`+`ReadOperand`（两次调用、两次边界检查）→ 一次索引 + 一次边界检查 | 189.2ms → 188.0ms（**−0.6%**） | 按"<5% 不算数"的纪律撤回，未提交 |

这个负结果本身有价值：它说明**取指不是主要瓶颈**，13ns/条里的大头是 switch
分派 + 栈操作 + 接口装箱的合成成本，逐个抠函数调用只会得到零点几个百分点。

#### 3.4.5 若要真做，第一刀应该切哪里

按上表的 flat 排序，第一刀是 1（值表示）+ 2（寄存器化），**而不是**任何单点
微优化。二者都不能在一个夜间批次内安全完成 —— 它们会同时改动 vm 与 compiler，
而这两处正是 test262 合规率攻坚（rFXXbq / rNaKtx）的战场。

## 4. 现有性能机制盘点
这些是**已经存在**的机制，本文只盘点、不改。它们是"为什么 gox 在 UI 侧不掉链子"
的答案，也标出了 M9 剩余工作（算力）的位置。

### 4.1 `gx/dev` 帧埋点（只数帧，不测耗时）

- 实现：`gfx/dev.go` 的 `devFrameTick(full bool)`，在 `redraw` 真正上屏的三个出口
  计数（`gfx/render.go`：整帧路径、>85% 面积退化、局部脏区路径）。
- 暴露：`gx/dev` 模块 `devSnapshot().frame` → `{ count, full, partial, fullRatio }`
  （`gfx/dev.go`；字段形状被 `TestDevSnapshotShape` 锁死）。
- **刻意的边界**：它**只做单调计数，不测 layout/draw 耗时**（源码注释原文：
  "耗时滑动平均等有真实需求再加"）。也就是说，仓库里**此前没有任何**帧间隔分布
  或 GC 停顿指标——这正是本次新增 `tools/perf/` 要补的那块。

### 4.2 image / glyph LRU 缓存

- **image LRU**（`gfx/image.go`）：`path → 解码后 *image.RGBA`，按**张数**上限
  `imageCacheCap = 16` 淘汰，统计 `{size, cap, hits, misses, evicts}`，经
  `devSnapshot().imageCache` 暴露。按张数而非字节数是有意为之（v1 不做按字节淘汰）。
- **glyph LRU**（`gfx/font.go`）：`(size, rune) → 字形掩码`，容量 `1024`，
  单线程 GUI 访问（锁仅防御），经 `devSnapshot().glyphCache` 暴露。
- 意义：把"重复解码图片""重复栅格化字形"这两个每帧最容易爆炸的分配源挡在渲染
  热路径之外——这一点在 [§5](#5-ui-帧率--gc-毛刺基准) 的分配速率里能看到效果。

### 4.3 `<scroll vlist>` 虚拟化

- 实现：`gfx/vlist.go`。只物化**视口 + 上下 buffer（缺省 2 行）**，上下用撑高
  垫片补出内容总高，滚动条/行程与全量渲染逐像素一致；容器已知但视口高未定时
  最多物化 `vlistPendingRows = 64` 行。
- 实测（`bench-results/vlist-20261001.json`，Windows / i7 机器）：
  | 行数 | 首帧 全量 | 首帧 vlist | 滚动帧 全量 | 滚动帧 vlist |
  |---|---|---|---|---|
  | 10 万 | 2187 ms | **89 ms** | 998.8 ms | **0.115 ms** |
  - 首帧与行数脱钩（vlist 恒 64 次渲染调用），滚动帧与行数完全脱钩。
- 判定纪律（原文结论）：**必须数"渲染调用次数"，不能数树上剩多少节点**——
  否则"先全建再销毁"的假虚拟化会骗过断言。

> 这是 GUI 渲染路径的成果，**不是解释器算力**。不要拿它去回答"fib28 慢"。

## 5. UI 帧率 / GC 毛刺基准

**位置**：`tools/perf/frame_gc_test.go`（包 `perf`）+ 压测脚本 `testdata/perf/frame_load.js`。

**跑法**：

```bash
go test ./tools/perf/            # 轻量探针 + 重压（默认）
go test ./tools/perf/ -short     # 只跑轻量探针（跳过重压）
```

### 5.1 测什么、为什么这么测

- **真实渲染**：脚本走真实 JS 建树（`gox` 模块 `h/render/createSignal`），
  每个 Go 侧"帧"调用一次 `__tick()`（更新若干行的独立 signal → 响应式 effect
  标脏），随后 `gfx.Pump` 走真实 `Layout` + 脏区 `Draw` + 上屏。**不建平台窗口**
  （用一个无窗口 `gfx.Surface` 替身），与 `gfx/vlist_bench_test.go` 的既有口径一致。
- **帧间隔**：相邻两次 `Surface.ShowRegions`（上屏）的时间差。它包含
  JS 更新 + effect + Layout + Draw + 任何 GC 停顿，是"用户眼里的掉帧"的直接代理量。
  用上屏时刻而非循环迭代时刻，是为了把"循环空转"排除在外。
- **GC 停顿**：`runtime/debug.ReadGCStats`，取**测量窗口内新增**的逐次 STW 停顿
  （`after.Pause` 的前 `NumGC` 差项）。只看分布尾部，不看平均值——毛刺只出现在尾部。
- **分配速率**：独立 goroutine 每 2ms 采一次 `TotalAlloc`/`HeapAlloc`，避免把
  `ReadMemStats` 的开销插进渲染循环。峰值 = 任意 1s 滑动窗口内 `TotalAlloc` 差分
  的最大速率。

> **退化说明**：gfx 包内测试用的 `fakeSurface` 是 `package gfx` 的**内部类型**，
> 外部包拿不到，因此 `perf` 自己实现了等价的 `perfSurface`（非阻塞 `WaitEvents`
> + 记录上屏时间戳）。这不影响测量对象（仍是真实 Layout/Draw 路径）。

> **重复运行与聚合口径**：重压默认重复 **3 次**（`PERF_STRESS_REPS` 可覆盖），
> 各分位取跨运行的**中位数**、`max`/GC 停顿 max/堆峰值取**最坏值**、GC 次数取**和**。
> 单次运行的尾部估计在无独占的桌面机上不稳，聚合后才可复现。

### 5.2 实测数据（Apple M2，2026-10-02，GOGC=100）

**轻量探针**（300 行、每帧更新 30 行、600 测量帧，单次，`perf-probe-20261002-025423.json`）：

| 指标 | 值 |
|---|---|
| 帧间隔 p50 / p95 / p99 | 0.77 / 1.67 / **1.71** ms |
| 帧间隔 p99.9 / max | 1.84 / 1.98 ms |
| GC 次数 / 停顿 max | 1 / **0.046** ms |
| 分配 平均/峰值 / 堆峰值 | 90.3 / 82.7 MB/s / 53.2 MB |

**重压**（800 行、每帧更新 200 行、2400 测量帧 × 3 次聚合，`perf-stress-20261002-025455.json`）：

| 指标 | 值 |
|---|---|
| 帧间隔 p50 | 3.35 ms |
| 帧间隔 **p95**（判定用） | **5.95** ms |
| 帧间隔 p99 | 9.68 ms |
| 帧间隔 p99.9 / max | 114.36 / 194.59 ms（参考） |
| 超 16.7ms 帧 | **6 / 2399 = 0.30%** |
| GC 次数（3 次合计） | 61 |
| GC 停顿 p50 / p95 / p99 / max | 0.100 / 0.329 / 0.628 / **1.382** ms |
| GC 停顿总计（3 次合计） | 10.71 ms（摊到 7200 帧 ≈ 1.5µs/帧） |
| 分配 平均 / 峰值 / 堆峰值 | 86.6 / 102.4 MB/s / 98.4 MB |

3 次单跑的离散度（说明为什么判定不能只看 p99/max）：

| 单跑 | p95 | p99 | max | GC 停顿 max |
|---|---|---|---|---|
| #1 | 7.40 | 12.42 | 194.59 | 1.382 ms |
| #2 | 4.39 | 6.74 | 132.53 | 0.316 ms |
| #3 | 5.95 | 9.68 | 120.72 | 0.664 ms |

可见 **GC 停顿始终亚毫秒~1.4ms**，而帧间隔的 p99/max 跨运行摆动很大（p99 6.7~12.4ms、
max 120~195ms；同日更早的运行里甚至出现 p99 36.8ms、max 366.8ms）。差异来自 OS 调度，
不是 GC。

### 5.3 "UI 无 GC 毛刺"的判定阈值

```
判定为「无 GC 毛刺」当且仅当:
  ① p95 帧间隔 ≤ 16.7 ms  (95% 的帧落在 60fps 单帧预算内)
  ② 单次 GC 停顿 max ≤ 5 ms (软件渲染 + 交互的可感知阈值)
```

- **为什么 16.7ms**：一帧 16.7ms = 60fps。用它作单帧预算；只要绝大多数帧不越界，
  用户就感知不到周期性掉帧。
- **为什么用 p95 而不是 p99/max**：无独占的桌面机上，p99/max 由 OS 调度抖动主导
  （同负载 3 次实测 p99 在 7~37ms、max 在 109~367ms 间摆动），拿它判会把"进程被别的
  进程抢了 CPU"误判成"GC 毛刺"。p95 跨运行稳定（实测 4.4~7.4ms），既覆盖了 95% 的帧，
  又不被尾部噪声绑架。
- **为什么 5ms**：交互/动画里 5ms 级停顿通常不可感知，10ms+ 才会在快速滚动时"顿一下"。
  本机重压实测 GC 停顿 max 仅 1.382ms，离阈值有 ~3.6 倍余量。
- p99 / p99.9 / max / 超预算帧占比仍**完整报告**，供人工判断；若某天真出现 GC 导致的
  长帧，它必然同时体现在"GC 停顿 max"上（因为长帧的 GC 成分直接可测）。

**当前判定**：① 5.95 ≤ 16.7 ✅；② 1.382 ≤ 5 ✅ → **无 GC 毛刺（达标）**。

> 硬闸门 vs 软判定：`perf` 测试只对"数量级劣化"硬失败（p99 > 200ms、
> GC 停顿 max > 100ms、重绘帧数异常），正常抖动不会让 CI 误报；上面的 16.7/5ms
> 阈值作为 `verdict` 写进 JSON，供验收引用。

## 6. GC 策略现状与 v1 决策

**现状**：gox 的 JS 对象全部是**普通 Go 对象**（`object.Value` / `*object.Object`
/ `*object.Array` …），由 Go 运行时分配与回收。**没有自研 GC**。

**v1 决策：依赖 Go GC，本轮不引入自研增量 GC。** 理由：

1. **零分配器控制权**：要自研增量 GC，前提是接管对象分配（自建 arena/空闲表）。
   但 `vm/`、`object/`、`stdlib/`、`gfx/` 全线用的是普通 Go `new/make`，接管等于
   重写分配器与所有对象生命周期，改动面与回归风险都极大。
2. **没有对象图所有权**：JS 对象与宿主 Go 对象（回调桥、闭包、signal effect）互相
   引用，精确根集无法界定；增量/分代 GC 需要 write barrier 与精确根，而 Go 运行时
   不对外暴露这些能力。
3. **收益/风险比不划算**：实测 UI 重压下 GC 停顿 max 仅 **1.382ms**（3 次聚合最坏值）、
   总计 10.71ms/7200 帧，离 5ms 可感知阈值有 ~3.6 倍余量、离"卡顿级"（>16.7ms）更是
   一个数量级——自研 GC 的收益近乎为零，却会引入 STW 正确性、并发正确性风险。
   自研 GC 与"单二进制 + 零 cgo"**并不冲突**（纯 Go 可写），但**不值**。

**后续可做的降分配与调优方向**（下一轮，按性价比排序）：

- **对象池**：热路径（fib 调用帧、数组/字符串临时对象、effect 闭包）复用，直接压低
  每秒分配字节数（当前 100 MB/s 量级）。
- **逃逸分析**：`go build -gcflags=-m` 找热路径上"本该在栈上却逃逸到堆"的分配，
  逐个消除。
- **旋钮调优**：`GOGC` / `debug.SetGCPercent` 权衡吞吐与堆占用；必要时用
  `debug.SetMemoryLimit`（Go 1.19+）给内存设上限，避免长时间运行后堆无限增长。
- 这些都**不是**"自研 GC"，而是把 Go GC 喂得更省。

## 8. goja 对照的口径与局限

- 位置：`bench/goja/`，**独立 Go module**（`goxbench/goja`），使主模块依赖面完全
  不受 goja 依赖（regexp2/sourcemap/pprof/x/text）污染。主模块 `go build ./...`
  不会进入嵌套 module。
- `bench/goja/main.go`：读 `scripts/bench/*.js` 同一批脚本，在 goja 里执行；
  **计时一律交给外层 harness**（与 gox/node 同源），runner 自身不打印耗时。
- 局限（如实写明）：
  1. goja 内核**不提供宿主定时器**，`timers_10k.js` 需要的 `setTimeout` 由一个
     **最小事件循环**（`container/heap` 按到期时间派发）补齐。因此 goja 的
     `timers10k_ms` **不是** goja 运行时调度器的性能，只作参考；gox/node 的该列
     才是各自真实定时器子系统的数字。
  2. goja 是纯解释器、无 JIT；这也正是把它作为 gox 同类基线的理由。
- 依赖拉取：从 `goproxy.cn` 成功拉取 `github.com/dop251/goja@v0.0.0-20261001174550-3ccc9c78af18`。
  离线时 `bench-compare.sh` 会**自动跳过 goja 栈**，gox/node 部分照常可跑。

## 11. 内存剖面与 RSS 闸门（T3-3）

§5 解决的是「帧有没有卡」，本节解决「挂久了内存会不会爬」。Gox 的渲染层是
无 GC 设计（帧缓冲 / 对象池手工复用），泄漏不表现为崩溃，只表现为 RSS 单调
上行——没有剖面和闸门，这种问题只能等用户投诉。

### 11.1 怎么开 pprof（常驻进程）

入口在 `cmd/gox/pprof.go`，由 `main()` 里的 `defer initPprof()()` 安装。
**默认关闭**：没设环境变量时只有两次 `Getenv`，不起 goroutine、不监听、不建
文件。两个变量各管一段：

```bash
# 1) 活着的进程：起 net/http/pprof（推荐只绑回环地址）
GOX_PPROF=127.0.0.1:6060 ./gox apps/notes/src/main.js
#    分配剖面（按分配字节数，找"谁在造垃圾"）
curl -s -o heap.pb.gz 'http://127.0.0.1:6060/debug/pprof/heap?alloc_space=1'
#    活对象（按当前占用，找"谁没释放"）
curl -s -o inuse.pb.gz 'http://127.0.0.1:6060/debug/pprof/heap'
#    火焰图 / 排行
go tool pprof -top -alloc_space ./gox heap.pb.gz
go tool pprof -top -inuse_space ./gox inuse.pb.gz

# 2) 抓退出那一刻：正常返回 或 SIGINT/SIGTERM 时 dump 一份堆剖面
GOX_MEMPROFILE=/tmp/heap.pb.gz ./gox apps/notes/src/main.js
#    Ctrl-C 后进程以 130 退出，文件已写好；-alloc_space 看分配，默认看 inuse
go tool pprof -alloc_space ./gox /tmp/heap.pb.gz
```

- 为什么用环境变量而不是 flag：`gox <入口.js>` 后面所有非 `--allow-*` 参数都
  会被当成脚本路径（`main.go` 的分发规则），加全局 flag 会污染脚本参数解析；
  而 `gox dev` 的热重启子进程只继承环境变量（`GOX_DEV` 同款通道）。
- 为什么 dump 要接管信号：仓库没有退出钩子，`os.Exit`（脚本报错 /
  `process.exit`）会跳过 `defer`；信号处理器覆盖了「人手动结束常驻进程」这条
  最常见的路径。
- 非回环地址会在 stderr 打一行警告：堆内容可能含业务数据，别随手绑 `0.0.0.0`。

### 11.2 怎么跑 RSS 闸门

在既有曲线采集上扩展，不另起一套：`tools/rssmon` 仍按进程树采 VmRSS 落 CSV，
`scripts/rss-curve.sh` 读完 CSV 再判定。

```bash
# 只采曲线（nightly 用这条，永远绿）
DURATION=120 INTERVAL=2 bash scripts/rss-curve.sh

# 带闸门（任一越界退出码 1；参数/环境错误退出码 2）
bash scripts/rss-curve.sh --max-rss 196608 --max-slope 512
# 等价的环境变量写法（CI 里更顺手）
RSS_MAX_KB=196608 RSS_MAX_SLOPE_KB_PER_MIN=512 bash scripts/rss-curve.sh
```

判定口径：

- **峰值**取全段 `max(rss_kb)`，包含 `gox dev` 的 watcher 父进程与子进程合计。
- **斜率**只回归**稳态段**（默认跳过前 30% 的样本）：启动期是一次性线性爬升
  （加载 JS、建窗口、解码图标/字体），算进去会得到一条假斜率。样本 < 10 个时
  不跳过（点太少，跳过更不稳）。
- 机器可读摘要：一组 `RSS_*` 键值行 + 一行 `RSS_SUMMARY {…}` JSON，例如：

```
RSS_PEAK_KB=141284
RSS_SLOPE_KB_PER_MIN=0.0
RSS_VERDICT=pass
RSS_SUMMARY {"csv":"bench-results/rss-notes-20261028T011459Z.csv","samples":60,
  "first_kb":4692,"last_kb":141284,"peak_kb":141284,"slope_kb_per_min":0.0,
  "max_rss_kb":196608,"max_slope_kb_per_min":512,"rss_ok":true,"slope_ok":true,"pass":true}
```

> 阈值为空 = 该侧不判（`null` 写进 JSON，不用 0 冒充"设过 0"）。
> 为什么闸门不默认打开：绝对 RSS 随机型/镜像/字体栈漂移，nightly 硬判会制造
> 噪声性红（同 `rss-curve.yml` 头部的理由）。

### 11.3 长时漂移测试

`tools/memdrift`（Linux；`-short` 跳过）：

```bash
go test ./tools/memdrift/ -v                       # 默认 7500 轮，约 2 分钟
MEMDRIFT_ITERS=500 go test ./tools/memdrift/ -v    # 缩短自查
go test ./tools/memdrift/ -short                   # 跳过
```

一轮 = 三件事，缺一件就漏掉一个泄漏面：

1. **求值**：新建一个 VM 执行一段小脚本（解析 / 编译 / 全局对象 / 200 个对象）；
2. **组件挂载**：`__churn()` 整批换掉列表数据，key 全变 → 旧行卸载、新行挂载；
3. **渲染**：`__tick()` 改行内 signal → 真实 Layout + 脏区 Draw + 上屏，每轮 6 帧。

判定前的纪律：

- 每 K 轮先 `runtime.GC()` 再采样。泄漏的定义是"GC 之后还活着的对象"，
  不 GC 只能测到"这一轮分配了多少"（那由 TotalAlloc 单独报）。
- 前 30% 只预热。字体/字形缓存、对象池、Go 堆首次增长都在这里一次性发生。
- 同时看两个信号：`HeapAlloc`（Go 堆活对象）与 `VmRSS`（进程实际占用）。
  后者能抓住"堆没涨但内存没还给 OS"——无 GC 设计最容易出这种。

**本次实测**（`bench-results/memdrift-20261028-012358.json`，本机 Linux，
640×480，200 行换批 + 6 帧/轮）：

| 指标 | 值 |
|---|---|
| 轮次 / 耗时 | 7500 轮 / 113.5s（15.0ms/轮，共 45000 帧） |
| 分配速率 | 261.5 MB/s |
| 稳态 HeapAlloc | 25144 → 25147 kB（**Δ +3 kB**，+2.0 kB/min；同日另一轮 +9 kB） |
| 稳态 VmRSS | 78016 → 78336 kB（**Δ +320 kB**，+318.3 kB/min；同日另一轮 +1524 kB） |
| 判定 | heap 3 ≤ 2048、rss 320 ≤ 16384 → **pass** |

> RSS 的 ±1 MB 摆动来自 Go 堆向 OS 归还页的节奏（采样序列在 77–80 MB 之间
> 来回），2 分钟窗口内回归出的斜率会随首尾点漂到几百 kB/min；因此闸门用
> **增量**判定，斜率只作报告（与 `--max-slope` 同单位，便于横向对照）。

### 11.4 阈值依据

| 指标 | 实测基线 | 闸门 | 余量 | 为什么这么定 |
|---|---|---|---|---|
| `rss-curve` 峰值 | 141284 kB（138.0 MB） | 196608 kB（192 MB） | ×1.39 | 覆盖字体栈/驱动差异；再高就说明常驻足迹确实涨了 |
| `rss-curve` 稳态斜率 | 0.0 kB/min | 512 kB/min | — | 8 小时挂机累计 ≤ 240 MB；能拦住"每帧漏一点"，又不被单次抖动触发 |
| 漂移 HeapAlloc | Δ +3~9 kB | Δ 2048 kB | ≥×227 | GC 后活对象很稳，卡紧才抓得住缓慢泄漏 |
| 漂移 VmRSS | Δ +320~1524 kB | Δ 16384 kB | ≥×10.7 | 留给堆高水位与归还节奏的摆动（跨机差异大） |

阈值 = **本次实测基线 + 余量**，不是拍脑袋的整数。机器/负载变了就重测重定，
不要直接把这两组数字抄到别的机器上。

### 11.5 已知盲区

1. **只覆盖 Go 堆**：`pprof` 看不到 gfx 手工池（帧缓冲、字形掩码）之外的
   cgo / GPU 显存；RSS 曲线能看到总量，但定位不到那里。
2. **`pprof` 抓不到硬退出**：`process.exit()`（内部是 `os.Exit`）与 `SIGKILL`
   不会触发 dump；只有正常返回、`SIGINT`、`SIGTERM` 会。需要必抓时用
   `GOX_PPROF` 活着抓。
3. **堆剖面是采样的**：默认每 512 KB 采一次，单个小对象泄漏可能一次 dump
   看不出来；要抓小泄漏就多跑一会儿、比较两次 dump 的差值。
4. **RSS 口径是 Linux `/proc`**：`rssmon` 与漂移测试都依赖它；macOS/Windows
   只有 §2 的外部 `time` 口径。`rssmon` 采的是**进程树**，`gox dev` 的父进程
   与子进程会合在一起，不能拿来拆"谁占了多少"。
5. **曲线含启动段**：`rss-curve.sh` 的峰值是全段峰值，包含启动期；闸门斜率
   已排除前 30%，但峰值没有——想只看稳态就自己裁 CSV。
6. **窗口反复开关存在已知泄漏（未定位根因，本任务范围外）**：临时探针实测
   （Linux，640×480，同进程内循环"新建 VM → 挂窗 → 关窗"）：
   - 平台关窗（`EventClose`，即用户点关闭 / 泵收到关闭事件）：40 轮后
     `windowHandles` 仍有 40 条（`gfx/render.go` 的 `a.close()` 只调
     `unregisterApp`，摘句柄只在 `Window.Close()` 里做），每轮额外留存一个句柄；
   - 脚本显式 `__root.close()`（句柄表为 0）：最小脚本仍约 **537 kB/轮**，
     200 行树约 **2.1 MB/轮** —— 说明还有一条未定位的保留路径，且与树大小
     相关，不是单纯帧缓冲（1.2 MB）。
   正因如此，`tools/memdrift` **整场只挂一个窗口**，把测量目标锁在"帧循环 +
   组件换挂"的稳态；窗口 churn 的修复需要改 `gfx` 内核，留给后续任务。

## 12. 冷启动到首帧（T2-5，2026-10-28）

单文件分发是 Gox 的卖点，"启动快"必须变成**可对外引用的数字**。本节补上
"冷启动到首帧"口径：**用户双击 exe 到看见第一帧像素**。两个口径，**不可混用**：

| 口径 | 位置 | 含进程 exec？ | 含真实窗口？ | 用途 |
|---|---|---|---|---|
| **进程级**（对外主口径） | `scripts/coldstart.sh` → `bench-results/coldstart-process-*.json` | ✅ | ✅（X11 真实上屏） | 宣传 / 发布说明 |
| **进程内**（CI 回归口径） | `tools/perf/coldstart_test.go` → `bench-results/coldstart-*.json` | ❌ | ❌（无窗口替身 Surface） | 每次提交的回归盯梢 |

### 12.1 对外可引用的数字

| 指标 | 值 | 说明 |
|---|---|---|
| **冷启动到首帧（含 GUI）** | **84 ms**（中位，n=15，单次 84–88 ms） | 进程 exec → 真实 X11 窗口首帧上屏 |
| 纯引擎启动（无 GUI） | ~4 ms（中位，n=5） | 进程 exec → 最小脚本求值完成 |
| GUI 首帧差额 | ~80 ms | 初步归因：**字体栈 ~65ms** > 窗口创建/X11 ~14ms > 引擎 ~4ms，见 12.3 |

**测量条件（引用时必须一并给出）**：

| 项 | 值 |
|---|---|
| 机器 | AMD EPYC 9K65（32 核），Linux 6.6 x86_64，123 GB 内存 |
| 显示 | Xvfb 虚拟显示 1024×768×24（软件渲染，无窗口管理器 / 合成器） |
| 版本 | gox 0.15.0（go1.26.2 构建，无 VCS 元数据），`scripts/bench/coldstart_gui.js` |
| 负载 | 最小 GUI 应用：一个 3 行 `column`，320×200 窗口 |
| 方法 | 外部 wall time，预热 2 次后跑 15 次取中位数 |
| 日期 | 2026-10-28（UTC） |
| 结果文件 | `bench-results/coldstart-process-20261028-122204.json`（n=15）、`coldstart-process-20261028-122100.json`（n=7）、`coldstart-20261028-122042.json`（进程内）、`bench-20261028-122136.json`（四栈对照） |

**进程内口径参考值**（同一机器同日，n=7 中位）：首帧 **0.79 ms**、求值全程 0.80 ms、
冷启动期分配 **1.0 MB**。这个数字不含进程 exec / Go runtime 启动 / 真实窗口创建，
只回答"引擎 + 模块装载 + 挂载 + Layout/Draw/上屏"本身多快，供 CI 回归盯梢。

### 12.2 跨运行时对照（JS 引擎侧）

与 node / bun / goja 的**同口径对照**只取引擎侧（`startup_ms`，外部 wall time 量
"进程启动 + 最小脚本求值"，四栈同源脚本）——JS 引擎本身可比：

| 栈 | 引擎启动 (ms) | 空载 RSS (KB) |
|---|---|---|
| **gox** | **3** | 16008 |
| node (V8/JIT) | 15 | 46580 |
| bun (JavaScriptCore/JIT) | 4 | 13624 |
| goja (纯解释器) | 2 | 7412 |

（同一机器同一批脚本，n=7 中位，2026-10-28，`bench-20261028-122136.json`。）

**诚实陈述**：

- gox 的引擎启动与 bun / goja **同级**（个位数 ms），明显快于 node —— 这一层
  **可以对外讲**："单文件分发 + 3ms 引擎启动"。
- **GUI 部分只对内不对外**：gox 的 84ms 首帧没有同口径的外部对照（electron /
  tauri 空壳需要各自的 GUI 环境与显示栈，本次未测，见 `bench-compare.sh` 的
  跳过纪律）。对外引用 84ms 时只说 gox 自己的条件，**不要**拿它和 electron 的
  启动数字直接相减 —— 显示栈不同，口径不可比。
- `fib28` / 定时器等算力列不在此引用（那是 §2/§3 的地盘）；只引用启动列时
  也要注意 gox 是纯解释器，不要与 JIT 栈的算力数字混为一谈。

### 12.3 口径细节与已知边界

1. **首帧信号是"像素真的出了"**：JS 侧用 1ms `setInterval` 轮询 `gx/dev` 的
   `devSnapshot().frame.count`（它只在 `redraw` 真正上屏的出口计数，见 §4.1），
   首帧后 ≤1ms 内被发现，打印标记后关窗退出 —— 全程含 **≤2ms** 探测/退出开销，
   已含在 84ms 里。**不用 `requestAnimationFrame`**：内核里它只是 16ms 的
   setTimeout（`gfx/render.go` 的 `jsRAF`），与真实上屏无关。
2. **首帧发生在 `render()` 求值内**：`gfx.Mount` 末尾同步调 `a.redraw()`
   （gfx/render.go "首帧"注释），所以进程内口径里 `first_frame_ms ≤ eval_ms`
   （实测 0.79 vs 0.80ms）。冷启动的主成本在求值前（引擎初始化 + 模块装载）。
3. **~80ms 的 GUI 差额：初步归因指向字体栈（2026-10-28 同机三档探针，n=7 中位）**：

   | 负载 | 首帧 (中位) | 增量 |
   |---|---|---|
   | 纯引擎（无窗口，`startup_idle.js`） | 4 ms | — |
   | 窗口 + 色块，**无文字**（`/tmp` 探针，未入库） | 18 ms | 窗口创建 + X11 往返 + 布局/绘制 ≈ **14 ms** |
   | 窗口 + 3 行 `text`（`coldstart_gui.js`） | 83 ms | **字体栈（查找/装载/栅格化）≈ 65 ms** |

   即首帧的最大成本是**画第一段文字**，不是窗口也不是引擎。这是后续启动优化
   的第一个靶子（候选方向：字体查找结果缓存、按需装载、栅格化延迟）。
   注意这是黑盒差分归因（没有 pprof 逐函数证据），精确归因待做；探针脚本
   未入库，复现时按 §12.1 的两个入库脚本自行二分即可。
4. **Xvfb ≠ 真桌面**：无 WM/合成器的软渲染环境数字**稳定可复现**（这是选它的
   理由），但真桌面/移动端真机的首帧口径不同（`docs/mobile-perf-baseline.md`），
   两套数字不可直接相减。换机器/显示栈须重测重写条件。
5. **进程内口径用无窗口替身 Surface**：与 §5 帧率基准同源（`perfSurface`），
   CI 无显示环境可跑；它测不到真实窗口创建的成本，所以不能替代进程级口径。

### 12.5 冷启动预算分解与 T3-5 后续批次（2026-11-17 夜批）

**为什么要分解**：§12.1 的 84ms 首帧里引擎只占 ~4ms，而"解释器初始化惰性化"
只能动这 4ms 里的一段。不做分解就会把 GUI/字体成本误算成引擎的账，也会高估
字节码缓存这类方案的天花板。

同一台机器（EPYC 9754，32 vCPU，Linux 6.6，go1.26.2）、同一日、外部 wall time
中位的预算表：

| 环节 | 中位 | 占引擎启动 | 量法 |
|---|---|---|---|
| 空 Go 程序（进程 exec + runtime 启动下限） | 1.52 ms | — | 同工具链编的 `func main(){}` |
| 依赖包 init 合计（131 个包） | 1.55 ms | — | `GODEBUG=inittrace=1` 累加 clock |
| `gox version`（全进程，不含解释器） | 4.16 ms | — | 300 次外部计时 |
| **`SetupGlobals`（解释器初始化）** | **0.35 ms** | 100% | `BenchmarkSetupGlobals` |
| 解析 + 求值 `startup_idle.js`（1 行脚本） | ~0.10 ms | — | `EvalFileVM` 微基准 − SetupGlobals |
| `gox startup_idle.js`（进程级合计） | 4.1–5.6 ms | — | 300 轮随机交错（随机器负载浮动） |
| 进程内首帧（替身 Surface，含 GUI 装载） | 0.92 ms | — | `TestColdStartToFirstFrame`，n=25 |

结论（对后续排期有用）：

- 进程启动里 **~3.1ms 是 Go runtime + 包 init + exec，与解释器无关**；能优化的
  只有 `SetupGlobals`（0.35ms）那一档。**解释器初始化再怎么惰性化，进程级
  天花板也只有 ~8%**。
- 包 init 的大头是 `object`（0.16ms，整型缓存等）、`esbuild/compat`（0.10ms，
  只服务 .ts/.tsx）、`gfx`（0.096ms）、`purego`（0.081ms）、`net/http/pprof`
  （0.064ms，仅 GOX_PPROF 用）。**引入字节码缓存对这几项零帮助** —— 它们发生在
  任何用户脚本之前。
- 二进制去符号（`-ldflags="-s -w"`，28MB → 21MB）**对启动无影响**（5.28 vs
  5.32ms，噪声内），说明 page-in 不是瓶颈；体积优化是分发成本问题，不是启动问题。

**T3-5 第二批（`b5692ef`）**：`applyBuiltinLengths` 改零分配路径下钻
（`splitRoot` + `setLengthFromNamePath`，惰性根判据前移），每次初始化少 549 次
堆分配。A/B（`tools/perf BenchmarkSetupGlobals`，-benchtime 2000x -count=5 中位）：

| 指标 | `16ade4f` | `b5692ef` | 变化 |
|---|---|---|---|
| ns/op | 379.1 µs | 352.1 µs | **-7.1%** |
| B/op | 344.7 KB | 320.4 KB | -7.0% |
| allocs/op | 2555 | 2006 | **-21.5%**（-549） |

进程级 `startup_idle` 中位 5.63 → 5.36ms（随机交错 300 轮/组，185/300 轮更快），
但 **min 持平（4.36ms）** —— 收益落在分配/GC 抖动而非指令路径，故对外仍以微基准
为准。进程内首帧 0.92~0.93ms 持平（首帧被 GUI 装载主导，见上表）。

**字节码缓存的可行性判断（基于上表，明确结论：本轮不做）**：

- 可缓存的部分是"解析 + 编译"。1 行脚本的解析+求值合计仅 ~0.10ms；即便是
  `apps/foldable-demo`（~30KB、4 个模块）这个量级的工程，编译也发生在毫秒以内，
  而缓存要付的代价是：缓存失效规则（脚本内容 / 引擎版本 / 内置模块解析路径）、
  单文件产物体积、以及首次运行仍要编译。
- 反过来说，**真正吃启动时间的是 GUI 首帧里的字体栈（~65ms，§12.3）**，
  量级是字节码缓存的 600 倍以上。启动优化应优先打那张牌，而不是缓存字节码。
- 触发条件（何时重开这个议题）：若某个真实工程实测"解析+编译 ≥ 5ms"且占引擎
  启动 > 50%，再按 `bench-results/perf-batch-*.json` 的口径重测。

### 12.6 T3-5 第五批：字体栈两次重复读盘（2026-11-17 夜批）

§12.3 把首帧的大头归给了字体栈；§12.5 又把进程启动拆到 0.35ms 的
`SetupGlobals`。本批顺着这条线往下走一步，问的是**字体栈内部**的时间花在哪。

**测量**（新探针 `gfx/TestColdstartFontStage`，`go test ./gfx/ -run TestColdstartFontStage`，
每次先 `resetFontCaches` 再计时，n=5 中位）：

| 阶段 | 基线 `6e19d53` | 本批 | 变化 |
|---|---|---|---|
| 目录扫描 `scanSystemFonts`（330 文件 / 148MB） | 50.5 ms | 36.9 ms | −27% |
| 选默认字体 `chooseBaseFont` | 17.0 ms | **0.01 ms** | −99.9% |
| **合计（首次用字体）** | **67.5 ms** | **37.7 ms** | **−44%** |

**根因（两处，都是"同一个文件被读了两遍"）**：

1. `chooseBaseFont` 拿到扫描候选后，把首个候选**从磁盘重读**一遍
   （`/usr/share/fonts/opentype/noto/NotoSansCJK-Bold.ttc`，19MB ≈ 17ms），
   而扫描刚刚解析过它。
2. 扫描阶段只留"正体面"，按族名取面（`fontFromSrc`）又把整份文件读一遍 ——
   `fontFamily` 一用就付。

**改法**：加一层进程级文件缓存 `fontFileCache`，键是路径、值带
`(mtime, size)` 身份校验（同进程内热替换字体不会被旧面骗过），值是**解析出来的面**
而不是字节（330 个文件的字节是 148MB，面只是几个指针）。扫描、选默认字体、
按族名取面三条路全部走这份缓存；"全部面"仍延迟到 `fontFamily` 首次使用时才解析。

**顺带的一个判断**：扫描本身剩下的 ~37ms 是**纯 IO**，不是解析 ——
Python 同机对照读同样的 148MB 是 36.7ms，`os.stat` 330 次只有 0.75ms。
所以"跳过已解析文件"救不了它，能救它的只有"干脆不扫"（见下）。

**进程级 A/B**（`scripts/coldstart.sh` 同源脚本 `coldstart_gui.js`，Xvfb :99，
两棵干净的 git worktree 各自 `go build`，随机交错 25 轮，外部 wall time）：

| 口径 | 基线 `6e19d53` | 本批 | 变化 |
|---|---|---|---|
| 首帧 中位 | 101.6 ms | **91.1 ms** | **−10.3%** |
| 首帧 min | 97.6 ms | 87.9 ms | −9.9% |
| 首帧 max | 105.5 ms | 97.0 ms | −8.1% |

25 轮交错里 25 轮都是本批更快（新二进制名次全胜是机器稳定的旁证）。

**没有变化的部分，如实记录**：

- `BenchmarkSetupGlobals` 306 µs / 324 KB / 2038 allocs，A/B 两侧完全一致 ——
  本批没碰解释器初始化。
- 进程内首帧 0.74 ms（基线 0.71–0.72 ms，n=7）：在噪声内。进程内口径用替身
  Surface，首帧前**不加载真实字体**，所以它本来就看不见这笔成本 ——
  这正是要另建分阶段探针的原因。
- 进程级 RSS 仍在 100–170MB 区间（同一二进制三次测出 99.8 / 173.2 / 121.0MB

**闸门（先建闸门再优化）**：`scripts/check-coldstart.py` 三条判据
（分阶段合计 / 进程级首帧 / 进程内首帧）。三条的阈值**故意不同**，理由各自不同：

| 判据 | 阈值 | 为什么 |
|---|---|---|
| 分阶段合计（扫描 + 选默认） | 1.25× | 与 check-bench 的 fib28 同档；它直接反映引擎在启动期做了什么 |
| 进程级首帧 | 1.25× | 对外口径；host 指纹变了降级为"只记录" |
| 进程内首帧 | **1.60×** | 绝对值只有 0.7–0.8ms，同树实测 0.68–0.86ms 区间（±30%），它守的是数量级劣化 |

配套两条纪律（都是"闸门自己被污染"的教训，来自 2026-11-17 夜批实跑）：

- **只认入库存档**：进程内首帧的默认数据源必须能被 `git ls-files` 列出来 ——
  一条命令连跑三份、或拿一份复制出来的工作树跑测试，都会留下时间戳更新的产物，
  顺手把"该比的数据"换成同一次跑批里被负载污染的那一份（实测 1.16ms vs 0.74ms，
  纯属噪声）。`--json` 显式指定时不受这条约束。
- **host 指纹只保留 (发行版, 架构)**：`Linux-6.6.117-45.11.6.tl4.x86_64-with-glibc2.39`
  这种串里的内核与 glibc 版本会随 runner 镜像升级而变，不归一就会把本该判红的
  回归降级成"只记录"。

`--self-test` 有 12 条负向自测（含"未入库产物不被采用""换发行版必须改变指纹"），
已进 `ci.yml` 的 Linux 作业。另有 `gfx/TestFontFileReadOnceAcrossScanAndChoose`
把"每份字体文件恰好读一次"钉成断言 —— 注：该断言当前是**红的**（见下）。

**已知遗留（下一批的入口）**：

- **断言仍红**：`TestFontFileReadOnceAcrossScanAndChoose` 在含系统字体扫描的

  （怀疑与 `resetFontCaches` 的时机/持有关系有关）。CI 里对应步骤会红，
  需下一批定位后再进闸门。**（第六批已定位并修复：根因是缓存里只存了 reg 面、
  取全部面要重读整份文件，见 §12.7）**
- **扫描仍是 ~37ms 的纯 IO**：真正的下一步是**不再扫**——按 mtime 落盘一份
  字体索引（"上次启动见过哪些可解析字体"），只在目录 mtime 变化时重扫；
  或反过来只信静态候选 + 首次使用时再补扫。两者都要先回答"字体装了/卸了
  怎么发现"，故本批不做。**（第六批未走这两条：扫描不判定就不必读盘，
  1.4MB 目录项 vs 148MB 文件，见 §12.7）**
- Linux 上 `chooseBaseFont` 会先验证一遍扫描结果（取首个正体），这轮验证命中
  缓存只花 stat，但如果将来把"正体判定"挪进扫描阶段，还能再省一次遍历。

7. **漂移测试的负载是压缩的**：2 分钟 7500 轮不等于"挂一夜"，它放大的是
   每轮分配/回收次数，抓不住"只在特定交互路径上触发"的泄漏。

### 12.7 T3-5 第六批：扫描不再读字体字节（2026-11-18 凌晨批）

上一批（§12.6）把"首次用字体"从 67.5ms 压到 37.7ms，并留下一句判断：
剩下的 37ms 是**纯 IO**，能救它的只有"干脆不扫"（落盘索引 / 只信静态候选），
而后两者都要先回答"字体装了/卸了怎么发现"，所以当时没做。

本批走的是第三条路，也是更短的那条：**扫描不该有 IO，是因为它本来就不该判定**。

- 扫描要回答的其实是"这台机器上有哪些字体"（= 读目录 + 看扩展名）；
- "这文件是不是真字体 / 它的正体面是谁"只有**真正被用上的那几个**才需要知道；
- 旧实现把两件事合成一件，于是为了 330 个候选的判定读了 148MB —— 而其中
  329 个从头到尾不会被渲染。

真伪与字重判定推迟到 `chooseBaseFont`（只解析到首个正体为止）与 `fontFromSrc`
（按族名取面才解析）那一刻。落盘索引要解决的问题（装了/卸了怎么发现）因此
根本不存在 —— 每次启动都重新"看目录"，只是不再"看内容"。

**顺带修掉上一批留下的红灯**：`fontFileEntry` 里存下 `Collection`，而不是只存
一张 `reg` 面。上一批的注释写着"缓存面而不是字节（330 个文件 148MB）"，
这句是错的：`sfnt.Font` 内部持的就是整份 `[]byte` 的引用，**每一张面都把整个
文件钉在内存里**。只存 reg 的真实后果是 `fontFileFaces`（按族名取面）必须
再读一遍盘 —— 于是 19MB 的 CJK 文件在一次启动里被读两次，
`TestFontFileReadOnceAcrossScanAndChoose` 因此一直红着。存 Collection 不多占
一个字节，却让那条路零读盘，红断言转绿。

**分阶段 A/B**（`gfx/TestColdstartFontStage`，两棵干净工作树随机交错 7 组，
每组内部 n=5 取中位；基线 `9fd17fc` / 本批 `25cc6ff`，同机 EPYC 9754 / Linux 6.6 /
go1.26.2 / 330 个字体文件 148MB）：

| 阶段 | 基线 | 本批 | 变化 |
|---|---|---|---|
| 目录扫描 `scanSystemFonts` | 57.31 ms（读盘 330 个文件） | **0.75 ms**（读盘 0 个） | **−98.7%** |
| 选默认字体 `chooseBaseFont` | 0.01 ms（全部命中缓存） | 14.80 ms（读盘 2 个） | 记账位置变了，见下 |
| **合计（首次用字体）** | **57.32 ms** | **15.50 ms** | **−73.0%** |

"选默认"变贵不是退步，是**记账位置的变化**：过去这 13ms 记在扫描账上（扫描
已经把 NotoSansCJK-Bold/Regular 两个 19MB 集合读完），现在扫描不读了，只有

**进程级 A/B**（`scripts/bench/coldstart_gui.js`，Xvfb 1024x768，外部 wall time，

**闸门（先建闸门再优化）**：新增

#### 第七批（判定视图）为什么被撤回

`7d6171d` 的出发点是"别把 148MB 读进内存"，做法是给 sfnt 喂一份只含判定表的
字节视图（name/head/post/maxp/hhea/hmtx/loca/cmap/CFF 头）。**前提本身不成立**：
`opentype.ParseCollectionReaderAt(*os.File)` 拿到的是 `io.ReaderAt`，sfnt 就是
按需 `ReadAt` 的，整次索引一共只读 29.1 MB（约每文件 88KB），从来不是 148MB。

于是在正确的基线上，视图层只是把同一份解析又做了一遍，还额外付了：

- 每个文件把表目录读两遍（12 字节头 + 整张目录）；
- 每次判定拼一份视图（紧凑排布 + 目录重写 + 校验和复制）；
- 大表（CJK 的 CFF、大 cmap）走 mmap，单次 4 次 CFF 探测读 + 映射/解映射成对系统调用。

结果是**两个维度都退步**：慢 2.3 倍（45.1 → 102.5ms）、多读 7MB（29.1 → 36.1MB），
而且它自带的 25ms 闸门从落地那一刻起就是红的。撤回记录见提交说明，视图层需要的
"逐面一致"验证（356 面比对）没有白做：那套口径被本批的一致性断言继承了下来。

> 口径提醒：`7.4MB` 的差值是**读盘字节**，不是"内存占用"。视图层声称省下的是
> 堆上的字形数据，但旧实现根本没把字形数据拷进堆 —— `sfnt.Font` 只持有
> `ReaderAt`，取名字时只碰 name/post。

#### 本批做法：三段式，合并留在单线程

1. `familyCandidatePaths`：按**稳定顺序**列候选（注入的随包字体 → 目录扫描 →
   静态候选），并去重（同一路径只解析一次）；
2. `parallelFor`：有界并发（`min(GOMAXPROCS, 16)`）把每个文件解析成纯数据
   `familyFaceEntry`（族名 / 样式轴 / 等宽标记），结果按路径下标落位；
3. `indexEntriesLocked`：单线程按路径顺序合并进索引。

**第 3 步必须单线程**：索引语义是"先到先得"（同族同轴取遍历顺序靠前的面，
否则同一台机器两次启动可能选到不同字重的面，渲染结果不可复现）。让并发结果
直接写 map，等于让 goroutine 调度决定胜者。这也解释了为什么"并发写 map + 加锁"
不是等价的简化：锁只保证不崩，不保证顺序。

并发度压到 16：每个任务开一个文件句柄，而目录里可能同时挂着几百个候选；
本机 16 路已接近饱和（32 路 26.5ms vs 16 路 27.8ms，在视图实现上量的），
再往上只是多抢 fd 与页缓存锁。

#### 闸门（先建闸门再优化）

`gfx/TestFamilyIndexBuildCost`，判据是**自校准比值**：同一进程、同一批文件、
同一份页缓存下量两遍 —— `workers=1`（等价于并发化之前的逐文件顺序调用）与
`workers=0`（自动并发），要求 **并发 ≥ 顺序的 1.33 倍**。

- 为什么不用"绝对毫秒 ≤ N"：第一版设的 25ms 在本机是绿的（13.8ms），但换到
  2 核 runner 上并发本身就要 ~25ms，**必假红**；而放宽到"不假红"的毫秒数
  又等于不设闸门。比值没有这个可移植性问题，它测的正是"并发有没有接上"。
- 为什么取**最小值**：干扰（GC / 邻居负载）只会让墙钟变大。同一份代码单独
  跑最小值 12.8ms，混在大套件里单轮能到 197ms —— 用中位或均值会让闸门自己
  变成噪声源。
- 负向自测（把 `parallelFor` 强制成 `workers=1`）：比值 0.99x，断言红。
  这就是它要拦的形态。
- `-race` 与 `GOMAXPROCS<4` 下跳过：前者插桩让墙钟失真一个数量级，后者并发
  收益与噪声无法区分（跳过而不是放宽阈值 —— 放宽等于让闸门永远绿）。

`gfx/TestFamilyIndexParallelMatchesSerial` 钉住"并发化不改变索引内容"：并发
建一份、逐文件顺序建一份，导出的快照（族 / 轴 / 面 / 别名 / 等宽，全部排序后
文本化）必须逐字节相同。这条比成本断言重要 —— 选错字重的面不会崩，只会画错。

两条断言都已进 `ci.yml` 的"冷启动闸门"步骤（Linux），与第六批的"扫描不读
字节"断言同批，红了会被归因到冷启动而不是普通测试失败。

#### 口径与边界（引用时必须一起给）

- 这 14ms 只发生在**脚本第一次用 `fontFamily`** 时，且是**首帧之后**的一笔；
  §12.1 的 55ms 首帧里**不含**它（不写 fontFamily 的应用一分钱不付）。
- 14.1ms 是**热缓存**数字（页缓存已含这 330 个文件）。冷缓存下每个文件仍要
  各自读盘，并发只是把等待重叠起来，收益按 CPU 占比折算，不能宣称"冷启动
  族索引 3 倍"。
- 并发度上限 16 是**本机**折中值；低核设备（移动端 4~8 核）按 `GOMAXPROCS`
  自动降级，脚本不需要改。

**复现命令**：

```bash
go test ./gfx/ -run 'TestFamilyIndexBuildCost|TestFamilyIndexParallelMatchesSerial' -v -count=1
go test ./gfx/ -run 'TestFamilyIndex' -race -count=1   # 成本断言在 -race 下自动跳过
```

| 路径 | 作用 |
|---|---|
| `gfx/familyindex_cost_test.go` | 成本闸门（min-of-5 ≤ 25ms）+ 并发/顺序一致性断言 |
| `gfx/race_on_test.go` / `gfx/race_off_test.go` | `raceDetectorEnabled`：让墙钟类断言在 `-race` 下跳过 |

### 12.10 T3-5 第十批：选默认字体不再整份读被否掉的候选（2026-11-18 夜批）

§12.7 把扫描从 148MB 读盘压到 0 之后，"首次用字体"只剩一步：`chooseBaseFont`。
当时它对本机是 **11.9ms，读 2 个文件**——因为 Linux 的候选表里
`NotoSansCJK-Bold.ttc` 排在 `Regular` 之前，而判"它是粗体、跳过"只需要 name 表，
旧实现却把整份 19MB 读进堆。**每一次启动都为"被否掉的那个候选"付一次整份读盘。**

本批把判面拆成两层：先用 `ParseCollectionReaderAt` 探针（只读表目录 + name 表，
每个文件 ~88KB）算出"这个文件里最好的面是几档"，**只有 rank==0 的那个才整份解析**
（栅格化确实要字形数据，这一笔省不掉）；整机没有正体面时的兜底也推迟到扫描结束
才读一份，而不是沿途每个候选都读。

#### 闸门（先建闸门再优化）

三条断言，全部进 `ci.yml` 的冷启动闸门步骤：

| 断言 | 判据 | 守的形态 |
|---|---|---|
| `TestChooseBaseFontReadsOnlyChosenFile` | 候选 `[粗体, 正体]`：粗体整份读 **0** 次，正体 **1** 次，读盘字节 ≤ 一个文件 | 为被否掉的候选付整份读盘 |
| `TestChooseBaseFontFallbackStillReadsOneFile` | 全机只有非正体面时，兜底仍返回可用面，且只读 **1** 个文件 | 兜底路径被写成"每个候选都读完" |
| `TestProbeFileFaceRankMatchesFullParse` | 机器上每个可解析字体：探针 rank == 整份解析 rank | **判错档位 = 默认字体选成粗体**（整屏变粗、`fontWeight` 看起来完全失效） |

负向自测（把探针替成"整份解析后取 rank"，即旧行为）确实红了：

```

无正体兜底时整份读了 3 个文件, 期望 1
```

### 12.11 T3-5 第十一批：判面/族索引不再建表（2026-11-18 夜批）

§12.10 把"为被否掉的候选整份读盘"堵掉之后，`chooseBaseFont` 还剩 **10.3ms**，
其中 6~7ms 花在 `NotoSansCJK-Bold.ttc` 的**探针**上。探针用的
`ParseCollectionReaderAt` + `col.Font(i)` 虽然不读字形，却会把每个面的
maxp/cmap/hhea/hmtx/post 全部解析建表 —— 10 个面各建一遍，而判面只用到 name
表里的一行子族名。同一形状的成本还藏在另一条路上：`fontFamily` 首次使用要建
族索引，旧实现把 330 个字体文件逐个整份解析，**26.5ms**。

本批写了一个极小的 sfnt 读取器（`gfx/font_probe.go`）：只读表目录 + name 表 +
post 表头，判面要的三样东西（子族名、italicAngle、isFixedPitch）全在里面。
两条路一起换过去：

| 路径 | 旧做法 | 本批 |
|---|---|---|
| 判面探针 `probeFileFaceRank` | `col.Font(i)` × 10 面（cmap/loca/hmtx 全建） | 表目录 + name + post 头，每面 ~8KB |
| 族索引 `scanFamilyFaceEntries` | 逐文件整份解析（330 个文件） | 同上，每文件 ~9KB |

**同时把判据收成单一实现**：`faceRank(sub, axis)` 与 `axisFromSubfamily(sub, angle)`
成为"整份解析"与"极小探针"共用的唯一入口。两条路各写一遍档位逻辑，就等于给
"默认字体选成粗体"留了两份可能漂移的判据 —— 这正是下面第二条闸门守的东西。

#### 闸门（先建闸门再优化）

| 断言 | 判据 | 守的形态 |
|---|---|---|
| `TestProbeReadsOnlyNameAndPost` | 探针读最大字体文件 ≤ **512KB**（实测 2,852 字节 / 文件 27,294,356 字节） | 有人在探针里加回整份解析或 `col.Font(i)` |
| `TestProbeNamesMatchFullParse` | 逐面比 family / typographic family / subfamily / 轴 / isFixedPitch，与整份解析一致 | 名字解码或 post 头判错 ⇒ 字重登记错 |
| `TestProbeFileFaceRankMatchesFullParse` | （既有）探针 rank 不得**比整份解析更悲观**（乐观只记日志，见下） | 判错档位 = 整屏变粗 / 默认字体跳过整个族 |
| `TestHasRequiredTables` | 9 条表组合：CFF / loca+glyf / CBLC 三个字形来源 + 缺表 + name 缺失仍可用 | 必需表清单改窄改宽都会先在这里红 |
| `BenchmarkFamilyIndexBuild` | 清缓存后重建族索引的耗时（不进闸门，只留轨迹） | 族索引退化没有曲线会红 |

负向自测就藏在第一条里：一旦探针退回 `col.Font(i)`，读盘量从 36KB 跳到 19MB，
阈值立刻红 —— 而毫秒断言在 CI 上看不出来（页缓存让整份读也显得便宜）。

**一处闸门重订**：`TestFamilyIndexBuildCost`（第九批的"并发必须比顺序快 1.33x"）
本批降到 **1.15x**。不是给回归让路 —— 第十一批把每文件成本砍掉 5.6 倍之后，
顺序建索引只剩 5.5ms，并发能拿到的只有调度重叠（读盘不再是瓶颈）。同一台机器
8 次取样落在 1.30~1.57，1.33 正卡在噪声带里，实测 8 次红 2 次。1.15 仍然挡得住
这条闸门真正要挡的两件事：并发没接上（=1.00）、新加的共享锁把并行串行化。

#### CI 上红过一次：探针"乐观"（macOS）

第一次推送后 macOS 作业红了两条 (`TestProbeFileFaceRankMatchesFullParse` /
`TestProbeNamesMatchFullParse`，后者还 panic)。两个都是**探针看得比整份解析多**：

| 现象 | 根因 | 改法 |
|---|---|---|
| macOS `HelveticaNeue.ttc`：探针 rank 0 / 整份 rank 1 | 该集合里存在"name 表可读、cmap 解析不了"的面。整份解析里这个面等于不存在，探针只看表目录看不到 cmap 的格式错误，于是多算了一个正体面 | ① 探针补必需表粗筛；② `chooseBaseFont` 遇到"探针 0、解析非 0"记成兜底而不是报错跳过整个候选 —— 判据以整份解析为准 |

### 12.12 T3-5 第十二批：字体按需读表（19MB → 2.8%）+ 冷启动采样口径修正（2026-11-19 凌晨批）

#### 12.12.0 先修口径：背靠背连跑给每个样本加了 ~14ms 的假成本

在动代码之前先做了一件更基础的事：**证明旧口径的数字本身不干净**。

用一个只做 `dial` + 握手的 xgb 程序（不建窗口、不碰字体），在同一台机器上
连跑三次：**0.25ms / 19.3ms / 19.2ms**；每次之间等 0.3s 再跑：**0.25 / 0.21 /
0.23ms**。三次结果一致。即：上一个客户端断开连接后，X server（这里是 Xvfb）
的清理会让下一条连接的 accept 晚 ~15ms。

`scripts/coldstart.sh` 旧版是**背靠背连跑**（`for i in $(seq 1 $RUNS)`，无间隔），
于是这个伪影被算进了每一轮。同一台机器、同一天、同一份脚本的对照：

| 采样口径 | base `0415008` | 本批 |
|---|---|---|
| 背靠背（旧口径，`--interval 0`） | 38ms | 26ms |
| 间隔 250ms（新口径，默认） | 24ms | **14ms** |

- 口径修正的幅度（~14ms）与优化收益（10ms）**同量级**。两者混在一起报，优化
  会被伪影吞掉或放大 —— 所以本节把两件事分开写，两套数字都给。
- 脚本改动：新增 `--interval <秒>`（默认 **0.25**），每样本后 `sleep`，并把
  `interval_ms` 写进结果 JSON 的 `method` 字段。`--interval 0` 可复现旧数字。
- **这是测量口径修正，不是性能优化**：24ms 与 38ms 描述的是同一份代码，
  不可相减、不可拿来说"省了 14ms"。

#### 12.12.1 靶子：首帧里 10.3ms 在读一份 19MB 的字体

用一次性的 env 开关（测完即撤，未入库）在 `mount → create-window →
layout → draw → present` 上打点，又在字体链路上按函数累加，单次进程 3 组一致：

| 阶段 | 耗时 |
|---|---|
| 建窗（xgb 连接 + CreateWindow + CreateGC + 属性 + 键盘映射 + Map + Sync） | **0.4 ~ 1.0ms** |
| Layout 合计 | 13.6 ~ 14.3ms |
| ├ `initFontCandidates`（330 个文件的目录扫描） | 1.4 ~ 1.6ms |
| ├ `chooseBaseFont` 探针（2 个候选：粗体被否、正体命中） | 0.55ms |
| ├ `parseFontFile`（`NotoSansCJK-Regular.ttc`，19,484,784 字节） | **11.0 ~ 12.2ms** |
| │　├ `os.ReadFile` | **10.3 ~ 11.5ms** |
| │　└ `opentype.ParseCollection` | 0.003ms |
| └ 字形栅格化（23 个，`face.Glyph`） | 0.12ms |
| Draw | 0.24ms |
| Present（XPutImage） | 0.6ms |

两个反直觉的结论：

1. **整份读盘的 10.3ms 里没有"解析"**。`opentype.ParseCollection` 只花 3µs ——
   sfnt 是惰性的，建 Collection 只读 TTC 头与每个面的表目录。钱全部花在
   `os.ReadFile` 把 19MB 拷进堆（`make([]byte, 19MB)` 清零 + 从页缓存 copy）。
2. **建窗不是 12ms，是 1ms**。§12.11 的归因表把建窗记成 11.4–13.2ms —— 那张表
   的插桩同样是背靠背连跑，量到的正是 12.12.0 里的 accept 延迟。所以 §12.11
   文末"下一批该打建窗"那条遗留**不成立**，真实建窗成本已经很低。

#### 12.12.2 改法：打开文件 + sfnt 按需 ReaderAt

`gfx/font.go` 的 `loadFontFileEntry` 从"整份读进堆"改成"保持文件打开 + 按需读表"：

| 旧 | 新 |
|---|---|
| `os.ReadFile(path)` → `[]byte` | `os.Open(path)`，句柄留在 entry 上 |
| `opentype.ParseCollection(data)` | `opentype.ParseCollectionReaderAt(fontFileReaderAt{ent})` |

配套的四个细节（都是踩过或想清楚了的）：

- **句柄不主动关**。`col` / `reg` / `all` 里每个 `*sfnt.Font` 都持有指向该句柄的
  ReaderAt，提前 Close 的形态是"首帧正常、后面某次重绘文字消失"（读到 EOF）。
  唯一该关的地点是 `resetFontCaches` —— 那里同时清掉 faceCache / facesByPath /
  glyphLRU，此后不可能再有人从旧 fd 取字形。
- **身份用已打开 fd 的 `Stat()`**，不用进入函数时那次 `os.Stat`：两次调用之间
  文件可能被换掉（fontconfig 刷新 / 包管理器升级），那时解析的是新文件而缓存
  记的是旧身份，之后会一直命中错的那一份。
- **替换旧 entry 时不关旧 fd**（文件被换掉的路径）。旧 Collection 可能还有 Face
  在用，泄漏一个 fd 比渲染报 EOF 好；真要清就等 `resetFontCaches`。
- **打开/解析失败立刻 Close**：候选表里有几十个坏文件（exe 改名的 .ttf），不能
  让它们变成几十个长期占用的 FD。

顺带给 entry 加了 `readBytes atomic.Int64`，由 `fontFileReaderAt.ReadAt` 累加 ——
这是闸门唯一能断言的事实（见 12.12.4）。

#### 12.13.1 靶子：1,128,457 次调用里有 1,028,456 次是 `fib` 递归

`CALL` 一共 1,128,457 条，其中 `fib` 帧内 1,028,456 条、顶层脚本 100,001 条
（for 循环里的 `add(t, i)`）。这 100 万次调用每次都做同一件事：

1. 从操作数栈弹函数、弹 `numArgs` 个实参，装进 `vm.callArgsScratch`；
2. 把切片传进 `callClosure`；
3. `callClosure` 再把切片里的值逐个写进 `frame.Locals`。

第 1 步和第 3 步是同一个搬运做两遍。行级剖面里 `Stack.Pop` 5.7% + `Stack.Push`
4.9%，其中相当一部分就是这个来回。

#### 12.13.2 改法：`callClosureFromStack` 直接按栈布局取参

`vm/callfast.go`（新文件）。`OP_CALL` 在**被调恰为普通闭包**（不是生成器函数、
没有形参前导段、没有待处理的直接 eval 标记）时走它：不碰复用缓冲，帧装配完成
后按"第 i 个实参 = `PeekAt(numArgs-1-i)`"落进 `Locals`，最后一次性
`Truncate(StackBase)` 把实参清出栈。

三个必须写清楚的点：

- **`StackBase` 要在截断之前算**：`callClosure` 里取 `Len()` 时实参已经弹掉了，
  所以这里取 `Len() - numArgs`，两者是同一个数。
- **先读实参、后截断**：`Truncate` 会清槽（帮助 GC），顺序反了就取到 nil。
- **为什么不抽公共函数**：公共函数要么接 `[]object.Value`（那正是要省的搬运），
  要么接一个取值接口（每读一个参数一次间接调用，比搬一次还贵）。所以两份
  装箱代码并存，`callfast.go` 里逐段注明对应 `callClosure` 的哪一段，**改一边
  必须改另一边**。
- **只开给"普通闭包"**：生成器与形参前导段要长期持有 args、直接 eval 要按调用
  点取调用者帧，这两条路仍走原路。fib28 里 1,028,456 次递归全部命中快路径。

#### 12.13.6 撤回记录：执行循环拆函数（改到一半，测不过，整批撤回）

本批一开始的靶子是行级剖面上的两处逐指令开销：`PendingGen` 判据（行 42，
90ms/1.19s）与调试快照三连写。做法是把循环顶部的两个判据挪到"指令执行之后"，
并把 `switch` 抽成 `runOps`。

**结论：在现有语义下不成立，撤回。** 依据（全部可复现）：

1. 抽出 `runOps` 后 `vm` 包 16 个用例红，核心形态是 `stack.Pop` 空栈 panic；
   进一步定位到"子执行在主程序执行期间跑完"时 `frameLeftover` 用
   `frameIdx == 0` 判主程序收尾，把回调的返回值当成整段脚本的完成值收走。
2. 加 `runRootIdx`（这段执行的起始帧）后 panic 消失，但 16 个用例仍有结果错
   （Promise adoption 停在 pending）。
3. **把改动缩到最小可复现形态**：只在基线树上把循环头部的两个判据原样搬到

   "帧收尾判据能否整体后移"这件事本身依赖于循环里的 `continue` 语义
   （有些 `continue` 会在本指令内换掉当前帧），不是可以机械平移的。

这条留作下一批的第一个动作：**先把 `continue` 与帧切换的全部耦合点列清楚**
（`OP_CALL`/`OP_RETURN`/`OP_NEW`/生成器冻结/try-catch 跳转），再决定新的收尾
判据放在哪里 —— 而不是先动代码再补语义。

### 12.14 T3-5 第十三批：字体文件缓存的内容指纹（2026-11-19 凌晨批，正确性修复）

本批**不产出性能数字**，它修的是前两批自己在 CI 上暴露出来的一个正确性洞：
缓存认错文件 ⇒ 用错误的字体渲染。这类问题必须当作 bug 处理，不能挂"性能优化"名下。

#### 12.14.1 现象：同一个用例在 Windows 上红，Linux/macOS 全绿

`TestFontFileCacheHonoursFileIdentity` 的做法是"写一份真字体 → 解析一次 →
把同一个路径改写成垃圾内容 → 再解析，必须报错"。缓存的身份判据是
`(size, mtime)`。用例自己留了一手：改写之后**把 mtime 显式往后推 2 秒**。

- Linux / macOS：mtime 秒级精度 + 显式后推 ⇒ 判据必然变化，绿。
- Windows（NTFS，LastWriteTime 精度 100ns）：`os.WriteFile` 覆盖写会**保留原
  mtime**，用例把 mtime 写回原值那一步又与"写文件"落在同一粒度里 ⇒ 判据完全
  没变 ⇒ 缓存命中 ⇒ 解析"成功" ⇒ 红。

结论：**旧用例不是"平台差异"，而是它靠一个偶然的时间后推躲开了洞**。任何人
在同一秒内热替换字体（换字体目录、包管理器升级、用户拖进一个同名文件）都会
踩到。先补 `TestFontFileCacheRejectsSameSizeSameMtimeSwap`（等长内容 + 原
mtime 的替换必须被认出），再修实现。

#### 12.14.2 第一版修法本身也有洞：指纹只存头部 4K 的**原字节**

第一版在 entry 上存 `sig [4096]byte` = 文件首 4K 的原字节（外加 size 折进末尾
8 字节），命中时重读首 4K 比较。它能挡住"换成垃圾内容"（第一处差异就在表头），
但挡不住**首 4K 相同、只有后面不同**的替换 —— 那正是"换了一份同族但不同版本
的字体""把字形数据改了"这类真实形态。契约写的是"内容变了就一定重读"，实现
只做到了"头部变了才重读"。

这是本批自己引入、又自己撤回的错误。改法是让指纹成为"片段 + 片段"而不是
"片段直接等于"：

```go
const (
    sigLen     = 4096                // 每次核对读的字节总量不变
    headSigLen = 3072                // 头 3/4: 覆盖 sfnt 表目录 + 前几张表
    tailSigLen = sigLen - headSigLen // 尾 1/4: 兜住"头部同字节、尾部不同"
)
```

`sig` = 「头 3072 字节」+「尾 1024 字节」的拼贴（`takeFontSignature`）。头部
覆盖表目录（表个数上限 4095、每项 16 字节，最坏 64KB，3KB 足以分辨正常字体的
表集合），尾部覆盖最容易随"换了一份文件"而变的内容。读盘量仍是每次 4K，改成
读两块（`ReadAt(off=0)` + `ReadAt(off=size-tailSigLen)`），对页缓存无感。

#### 12.14.3 闸门

| 断言 | 形态 | 守的是什么 |
|---|---|---|
| `TestFontFileCacheHonoursFileIdentity` | 换成非字体 + mtime 后推 | 最基本的"文件换了要重读" |
| `TestFontFileCacheRejectsSameSizeSameMtimeSwap` | 等长垃圾 + 原 mtime 写回 | Windows 上 `os.WriteFile` 保留 mtime 的形态 |
| `TestFontFileCacheRejectsTailOnlySwap` | 首 4K 完全相同，尾字节翻一位 | **第一版指纹的洞**：指纹只覆盖头部时必红 |
| `TestFontFileCacheMissDoesNotUseStaleFingerprint` | 内容不变连取两次 | 防"判据过严 ⇒ 每次都重解析"，反向守性能 |

身份用例都走 `loadFontFileEntry`（而不是上层的 `parseFontFile`），因为身份判定
发生在 entry 层 —— 走上层会把"缓存命中"与"另一个目录级缓存命中"混在一起，
红了也说不清是谁的问题。

样本目录**不用 `t.TempDir()`**（`useFontSampleDir`）：缓存命中时会持有被缓存
文件的 fd 直到 `resetFontCaches`，而 Windows 上"文件还被打开着"的目录删不掉，
`t.TempDir` 的自动清理会报 `The process cannot access the file because it is
being used by another process` —— 用例本身全过、却在 cleanup 阶段红掉。顺序改
成"先 `resetFontCaches` 放 fd，再删目录"。

CI 侧补一步**三平台**跑的 `go test ./gfx/ -run TestFontFileCache`，不挂
`if: runner.os == 'Linux'`：这条纪律恰恰是在 Windows 上被打破的，只放在 Linux
那一步里等于"只在不会犯错的平台上验"。该步骤必须**显式 `shell: bash`**（不写
就是 pwsh，`rc=$?` 在那里面不存在），并且**不要 `if ! go test`**（会把命令输出
吞进条件里，注解只剩一句 exit code 1）—— 这两条都是当天实际踩过的坑。

#### 12.15.1 先量清楚 14ms 花在哪（§12.12.5 遗留的第一条）

#### 12.15.2 靶子：`refreshDensity` 每帧三次同步往返

`Layout` 第一行是 `refreshDensity()` —— 它要回答"本帧 dp 系数是多少"，答案取决于
窗口落在哪块屏。旧实现是**每帧现场问**：

```
refreshDensity → resolveDensity → DisplayOf(surface)      ← TranslateCoordinates + QueryVersion + GetMonitors
                                → findDisplay(id) → Displays()  ← 再枚举一遍
```

实测各查询的往返成本（同机 Xvfb，各 300 次平均）：

| 调用 | 单次 |
|---|---|
| `TranslateCoordinates` | 12.3 µs |
| `randr.QueryVersion` | 10.8 µs |
| `randr.GetMonitors` | 13.5 µs |
| **合计（旧路径每帧）** | **36.6 µs** |

即：**60fps 的帧预算 16.7ms 里有 0.22% 花在"确认我没被挪到别的屏上"，而窗口根本没动。**

#### 12.15.3 改法：事件驱动作废 + 建窗播种

| 旧 | 新 |
|---|---|
| 每帧 `DisplayOf` + `Displays()` | 缓存命中时**零后端调用**（一次指针比较） |
| 作废条件只有"窗口换了" | 再加一条：后端报"这块窗口可能换屏了" |
| 无 | 建窗后播种一次（`NoteSurfaceCreated`），首帧前确定归属 |

作废信号（全部经已有的事件通道，不新增轮询）：

| 后端 | 信号 | 现有接线 |
|---|---|---|
| X11 | `ConfigureNotify` | `PostWindowDisplayCheck` → `CheckWindowDisplay` |
| X11 | RandR `ScreenChangeNotify`（插拔屏 / 改分辨率） | **本批新增**：建窗时 `SelectInput(NotifyMaskScreenChange)`，事件 → `NotifyDisplaysChanged` + `PostWindowDisplayCheck` |
| win32 | `WM_DPICHANGED` / `WM_DISPLAYCHANGE` | 已有 `PostWindowDisplayCheck` / `NotifyDisplaysChanged` |
| cocoa | `NSWindowDidChangeScreen` / `NSApplicationDidChangeScreenParameters` | 已有 `CheckAllWindowsDisplay` / `NotifyDisplaysChanged` |
| 全部 | 建窗完成 | **本批新增** `gfx.NoteSurfaceCreated(s)`（x11 / win32 / cocoa 各一处） |

语义为什么仍然正确：**系数在"事件到达之后的第一次布局"就更新**，而"没事件"就意味着
"窗口没换屏"（三个后端的换屏事件都是系统级通知，不依赖轮询）。这正是"每帧刷"要保的
性质，只是把判断从"每帧问"换成了"事件告诉我"。

在 X11 上是 **36.6µs**（12.15.2 实测往返），差 200 倍。所以本批的正确表述是：

- **每帧省下一次同步往返（X11 36.6µs、≥3 次 socket RTT），这是结构性的、与后端实现无关的收益**；
- **体现在首帧上的收益是 −0.1ms / 噪声带内** —— 因为首帧只有两次布局，而 14ms 里
  5ms 是进程启动、3.6ms 是树遍历；
- **不把它写成"冷启动快了 X%"**，也不写"省了 36µs×N"这种外推。

#### 12.15.5 闸门（先建闸门再优化）

| 断言 | 守的形态 |
|---|---|
| `TestLayoutDensityNoBackendRoundTrip` | 连续 6 次 Layout，后端只能被问 1 次（首次）——缓存被关就红 |
| `TestDensityScaleFollowsWindowAcrossScreens`（既有，改为经 `CheckWindowDisplay` 驱动） | 换屏后下一帧必须按新系数 |
| `TestLayoutDensityFollowsWindowMove` | 换屏 → 作废 → 重算，且能来回 |
| `TestCheckAllWindowsDisplayInvalidatesCache` | cocoa 那条逐窗口入口也作废（漏了就 mac 上不重排） |
| `TestLayoutDensityNotifyOtherSurfaceKeepsCache` | 别的窗口换屏不拖累本窗口 |
| `TestNoteSurfaceCreatedSeedsOnce` | 播种之后首帧只问一次、后续零次 |
| `TestDisplayScaleUncachedPathStillResolves` | 没走过 Layout 的读数仍现场解析（不许恒为 0/1） |

反向验证：把 `refreshDensity` 的缓存判断改成永远不命中，`TestLayoutDensityNoBackendRoundTrip`
与 `TestLayoutDensityNotifyOtherSurfaceKeepsCache` 立刻红；改回即绿。

CI 新增一步 **「密度缓存纪律（每帧不查后端）」**，**不挂 `if: runner.os`** ——
退回去的形态三平台共有，而这条纪律恰恰不该只在 Linux 上验。

#### 12.15.6 遗留

- **`Layout` 的 3.1~3.4ms 树遍历**是首帧里最大单项（23 行、4 个节点的小树也用掉
  3.4ms —— 说明其中有大头与节点数无关）。下一批应当先在这个数上取证（pprof 到函数级，
  §12.12.5 说的"缺 pprof 逐函数证据"仍未补）。
- **`startup_idle` 的 6ms 里约 2.7ms 是 Go runtime 启动地板**（空 Go 程序同价）。
  想过 `-ldflags=-s -w` 与去掉 `net`/`crypto` 的链接，但那是"二进制体积/启动"另一个
  话题（T3-6），且会改变 panic 栈信息，不在本批动。
- 移动端宿主（Android / 鸿蒙 / iOS）的 `NoteSurfaceCreated` 未接 —— 那些平台的密度
  由宿主上报，`displayScale` 走的是"无缓存现场解析"路径，行为与改动前一致（不会更慢
  也不会更快），接线留到对应宿主改动时一并做。
